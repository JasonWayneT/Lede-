# Architecture Decision Record: ADR-005 Audio mixing via numpy + scipy + soundfile (no new dependency)

## Status

accepted

## Context

Music Roadmap Phase 5 lays the selected music beds under narration and renders the structural
(intro/outro/section-transition) stingers into the single `briefing.mp3`, using the segment plan +
per-segment durations that Phase 4 produced (`FR-030`). The core question was which audio toolkit
to mix with, given the format mismatch (Kokoro narration is 24 kHz mono; music clips are 44.1 kHz
stereo) and Lede's local-first, easy-install constraints.

Verified during design: `scipy` 1.17.1 (with `signal.resample_poly`) is already present
transitively, `numpy` is present, and `soundfile` both reads the MP3 clips and writes MP3. So a
numpy-based mixer needs **zero new dependencies**.

## Decisions

**1. Mix with numpy + scipy + soundfile — not pydub or ffmpeg.**
The operations are simple: gain (`10**(db/20)` multiply), linear fades (ramp multiply on a sample
range), loop-to-length (`np.tile` + trim), duck-and-sum (add arrays), clip guard (scale if peak >
0.99). The only non-trivial step is resampling, handled by `scipy.signal.resample_poly`. This keeps
mixing in the same numpy/soundfile idiom `tts.py` already uses, makes every mixing primitive a pure
function unit-testable on sample arrays with no binary, and adds no dependency to flag against
`AGENTS.md`.

Rejected: **pydub** — ergonomic but requires the ffmpeg *binary at runtime for the app*, which
works against `NFR-007` (non-expert setup under 15 min) for a local-first app; also semi-unmaintained.
Rejected: **ffmpeg `filter_complex`** — powerful but variable-length filtergraph string-assembly is
brittle and hard to unit-test.

**2. Target format is 44.1 kHz stereo.**
Music is the fidelity-sensitive layer; upsampling mono narration to 44.1 kHz stereo (duplicate to
both channels) is cheap and lossless-ish, whereas downmixing music to 24 kHz mono would audibly
degrade the beds — the wrong trade for a polish feature.

**3. Mix inline in `tts.synthesize_plan`; do not persist per-segment audio.**
This resolves Phase 4's open "persist vs. re-render" question in favor of *neither*: for each
segment, render narration (narrated segments) or nothing (structural), mix with `mixing.py`,
concatenate, write the single mp3 — one pass. No intermediate per-segment files. `duration_seconds`
is now the *mixed* segment length.

**4. Mix profiles are keyed by `story_weight` (stories) and role (structural).**
Values are adapted from the original report's section 21. `story_weight` (classified by frame in
Phase 2, `FR-028`) is threaded through `draft` → `tts_prep` → the segment so mixing can pick the
profile — completing the classification→mixing path that justified classifying it. Sensitive/crisis
stories already resolve to no music (Phase 3), so they mix as dry voice; a `sensitive` story profile
exists only as a floor.

**5. Music-less and missing-file cases degrade to dry voice, non-fatally.**
A story whose `selected_music` is `None` (sensitive, or unmapped section with no asset) mixes as
narration-only. A `selected_music` whose file is missing on disk logs a warning and falls back to
dry voice rather than failing the run — consistent with `FR-011` (audio non-fatal).

## Consequences

### Positive

- No new dependency; stays in the codebase's numpy/soundfile idiom; every primitive unit-testable.
- Structural segments become audible for the first time.
- Completes the full classification → selection → segmentation → mixing path end to end.

### Negative

- Hand-rolled DSP (fades, loop, duck) is more code than pydub's one-liners — mitigated by the ops
  being genuinely simple and well-tested.
- Mix-profile numbers (gain/duck/fade) are first-pass estimates; they can only be tuned by ear
  (Phase 6). Encoded as named constants so tuning is a one-place edit.
- Looping a 30 s clip under a long story repeats the music; acceptable for V1 (a longer or more
  varied library is deferred to V2 per the roadmap).

### Neutral

- True crossfades between segments are deferred; segment boundaries use the per-segment fades only.

## Alternatives considered

| Option | Why rejected |
|---|---|
| pydub | Runtime ffmpeg-binary dependency vs. local-first easy-install goal; semi-unmaintained |
| ffmpeg `filter_complex` subprocess | Brittle programmatic filtergraph assembly; hard to unit-test |
| 24 kHz mono target (simpler) | Audibly degrades the music beds — defeats the point of the feature |
| Persist per-segment audio files for mixing | Unnecessary once mixing is inline in the render loop; adds disk + a lifecycle to manage |
