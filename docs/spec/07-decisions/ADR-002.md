# Architecture Decision Record: ADR-002 Music classification uses two fields (sensitivity, story_weight), not four

## Status

accepted

## Context

The original music policy report (see `docs/music/ROADMAP.md`) specified a four-field
classification per segment: `emotional_tone`, `story_weight`, `sensitivity`, `music_intent`, plus
an 8-topic `topic_category` axis feeding a 20-style music bank. Phase 1 of the music roadmap
already cut the style bank down to 6 styles, mapped 1:1 to Lede's actual configured sections
(`AI`/`Technology` → `modern_tech_digest`, `Finance` → `business_briefing`, `Politics` →
`civic_affairs`, `Other`/fallback → `warm_daily_briefing`, plus the two structural styles
`premium_newsletter_intro` and `headline_transition`).

Given that cut, `topic_category`/`music_intent` (which existed to arbitrate between many styles
per topic) has no remaining job for V1 — Phase 3 selection can key directly off the `section_name`
field `frame.py` already produces (`FR-006`), since each section already maps to exactly one V1
style. Likewise, `emotional_tone` was intended to feed the scoring engine (deferred to V2+) and
the mix profile (which V1 keys off `story_weight` instead, per the roadmap's mix-profile-level
defaults decision) — it has no V1 consumer either.

## Decision

`frame.py`'s existing structured-output call (`FR-007`) gains exactly two new fields:

- `sensitivity`: `normal | serious | sensitive | crisis` — gates whether music plays at all.
  `sensitive`/`crisis` stories get no music, overriding whatever the section-to-style map would
  otherwise pick (Phase 3).
- `story_weight`: `light | medium | heavy | sensitive` — tunes mix intensity (Phase 5 mix
  profiles), independent of whether music plays at all.

`emotional_tone`, `music_intent`, and `topic_category` are not implemented for V1. Style selection
(Phase 3) uses the existing `section_name` field directly.

## Requirement links

- `FR-028`
- `FR-006` (existing section assignment, reused as the style-selection key)
- `FR-007` (existing frame stage, amended)

## Consequences

### Positive

- One LLM call, two new fields, both validated against fixed enums with safe defaults — smallest
  possible change to an already-working, tested stage.
- No redundant classification axis: `section_name` already exists and already maps 1:1 to the V1
  style set; adding `topic_category` alongside it would just be two names for the same fact.

### Negative

- If V2 ever needs finer-grained style selection than "one style per section" (e.g. multiple
  candidate styles per section, arbitrated by tone), `emotional_tone`/`music_intent` will need to
  be added back at that point — this is deferred cost, not eliminated cost.
- `story_weight`'s allowed value `"sensitive"` and `sensitivity`'s allowed value `"sensitive"` are
  the same string naming two different axes (weight tier vs. content sensitivity) — inherited
  directly from the original report's enums, not renamed here to keep continuity with what was
  already reviewed. Worth revisiting if it causes confusion in practice.

### Neutral

- None.

## Alternatives considered

| Option | Why rejected |
|---|---|
| Implement all four original fields (`emotional_tone`, `story_weight`, `sensitivity`, `music_intent`) | Two of the four have no consumer until a scoring engine exists, which is explicitly deferred; adding unused fields now violates the same YAGNI standard applied to Phase 1's style-count cut |
| Add a new `topic_category` field distinct from `section_name` | Redundant — sections already map 1:1 to V1 styles; two fields naming the same fact invites drift if a section is ever renamed and the new field isn't updated in lockstep |

## Supersedes

- None
