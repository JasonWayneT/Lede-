# Architecture Decision Record: ADR-001 Conditional source condensation instead of fixed-size truncation or fixed-window chunking

## Status

accepted

## Context

Frame and draft stages each independently truncated every source's cleaned text to a fixed
character count (300 and 500 chars respectively) before building their LLM prompts. Combined with
`BUG-001` (Ollama's context window silently capped at 2048 tokens), drafted stories read as
generic, headline-level prose — the model was never given enough real source material to write
anything substantive.

The PM's first instinct was to chunk every source into small fixed windows (~300 characters) and
feed them through sequentially, reasoning that this would bound the local model's context usage
and reduce hallucination risk. Investigation showed two problems with that specific shape:

1. Fixed-size character windows cut mid-sentence. A local 7B-class model asked to interpret a
   fragment with no surrounding context is *more* likely to hallucinate to fill the gap, not less.
2. It solves the wrong constraint. The actual ceiling was Ollama's un-set `num_ctx` (2048 tokens,
   see `BUG-001`), not the source text itself — a qwen2.5:7b model natively supports 32K tokens.
   Chunking every source, including short single-paragraph newsletter items that already fit
   comfortably in budget, adds LLM calls and hallucination surface for no benefit.

## Decision

1. Fix `BUG-001`: explicitly set `options.num_ctx` on every Ollama request from a new
   `AppConfig.ollama_num_ctx` field (default `8192`).
2. Replace the two independent, inconsistent hard truncations (300 chars in frame, 500 chars in
   draft) with one shared per-source character budget (`SOURCE_TEXT_BUDGET_CHARS = 4000`,
   `app/services/condense.py`), used identically by both stages.
3. Condensation is **conditional**, not universal: a source under budget passes through unmodified.
   Only a source whose cleaned text exceeds the budget is condensed.
4. Condensation is a single **map pass, no separate reduce LLM call**: the oversized source is
   split on sentence boundaries (never mid-sentence) into chunks near `CONDENSE_CHUNK_CHARS`
   (3000 chars), each chunk is sent through an extraction-only prompt
   (`pipeline_prompts/stages/condense.md`: "list only facts explicitly stated, no inference"), and
   the per-chunk outputs are concatenated. The existing frame/draft stages act as the reduce step —
   they already synthesize across multiple sources in a cluster, so no additional LLM hop is added
   on top of the map step.
5. Chunking splits on sentence boundaries, not paragraph breaks. `extract.py`'s whitespace
   normalization (`_WHITESPACE = re.compile(r"\s{2,}")`) collapses most paragraph-separating
   newlines to a single space, so paragraph structure is not reliably present in `entry["text"]` by
   the time it reaches condensation. Sentence-boundary splitting is robust regardless of whether
   paragraph structure survived extraction.
6. Frame stage computes `source_texts` (list of per-entry condensed-or-original text, one per
   cluster source) once and carries it forward on the framed story dict. Draft stage reads
   `story["source_texts"]` directly instead of re-deriving/re-truncating from the raw cluster —
   avoiding a duplicate condensation pass and resolving the prior 300-vs-500-char inconsistency
   between the two stages. If `source_texts` is absent (e.g. an older persisted handoff artifact
   from before this change, used in a partial rerun), draft falls back to computing it per-entry
   itself.

## Consequences

### Positive

- Single-source stories (the common case observed in production) now pass through their full
  cleaned text instead of a ~500-character teaser, directly fixing the "reads like headlines, not
  a real explanation" complaint.
- One shared budget constant, one place chunking logic lives — frame and draft no longer disagree
  on how much of a source they've each seen.
- Extraction-only map prompts ("facts explicitly stated, no inference") keep the hallucination
  surface small for the rare long-source case, without adding a second synthesis/reduce LLM pass.
- `num_ctx` fix benefits every Ollama-routed stage, not just frame/draft.

### Negative

- Sources that exceed budget now cost 1+ additional LLM calls (one per ~3000-char chunk) before
  framing/drafting even starts — added latency for long-form sources specifically.
- `CONDENSE_CHUNK_CHARS`/`SOURCE_TEXT_BUDGET_CHARS` are fixed constants, not derived dynamically
  from `ollama_num_ctx` or the active provider's real limit. If `ollama_num_ctx` is later lowered
  significantly, these constants would need to be revisited manually.
- A source with no sentence-ending punctuation (e.g. a bullet list with no periods) still produces
  one oversized chunk rather than being split further — accepted tradeoff to avoid re-introducing
  mid-fragment cuts.

### Neutral

- Raising `ollama_num_ctx` increases Ollama's memory usage per request; exact impact depends on the
  user's hardware and is not benchmarked as part of this change.

## Alternatives considered

| Option | Why rejected |
|---|---|
| Fixed ~300-char rolling chunks for every source, always | Cuts mid-sentence, increases hallucination surface, adds LLM calls even for sources that already fit comfortably in budget |
| Chunk + separate LLM reduce/merge pass per source | Each extra LLM hop is another chance for drift; frame/draft already perform the reduce step across a cluster's sources |
| Derive chunk size dynamically from `ollama_num_ctx` per request | Adds complexity for a value that only matters for the Ollama provider; fixed conservative constants are safe across all providers and simple to reason about |
