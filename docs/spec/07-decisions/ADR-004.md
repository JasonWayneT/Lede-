# Architecture Decision Record: ADR-004 Audio segment plan built from drafted stories; music-only structural segments

## Status

accepted

## Context

Music Roadmap Phase 4 (`docs/music/ROADMAP.md`) is the enabling restructure: per-segment music
requires the audio to be built from discrete segments with known durations (intro / each story /
each transition / outro), instead of today's single whole-briefing synthesis. Investigation of the
existing audio path surfaced three constraints that shaped the design:

1. **`tts_prep` currently runs on empty markdown (`BUG-005`).** It reads `packet.assembled_markdown`,
   which the `assemble` stage (position 9) writes *after* `tts_prep` (position 8). So the narration
   script is generated from an empty string today.
2. **Three synthesis call sites** all read `packet.tts_script` and write `briefings/{run_id}/briefing.mp3`:
   the main pipeline, the on-demand (YouTube/article) pipeline, and the resume/re-synth path in
   `app/api/briefings.py`. Any restructure must keep all three producing that single file, non-fatally
   (`FR-011`).
3. **No audio-mixing dependency** (`pydub`/`ffmpeg-python`) is installed — audio is `numpy` + `soundfile`
   at 24 kHz mono. Concatenation is trivial; mixing (resample + overlay of 44.1 kHz stereo music) is a
   Phase 5 problem, deliberately out of scope here.

## Decisions

**1. Build the segment plan from `packet.drafted_stories`, not `assembled_markdown`.**
`drafted_stories` is produced by `draft` (stage 7) and is always populated before `tts_prep` (stage 8).
Deriving the plan from it fixes `BUG-005` by removing the dependency on a later stage entirely, and
gives per-story structure (prose + `section_name` + `selected_music`) for free — exactly what the
segment plan needs.

**2. Narration text is the story prose, cleaned deterministically — not an LLM rewrite.**
`draft.md` already enforces broadcast prose (no markdown, no bullets, no URLs). The only cleanup
needed is stripping the `> Sources: …` attribution trailer `draft.md` appends. So per-story narration
is a deterministic transform of existing prose. The one thing worth an LLM is the pronunciation guide
(a flat term→spelling dict), which `tts_prep` still produces via a single non-fatal LLM call over the
concatenated narration. This keeps LLM cost at one call (same as before) and avoids the fragile
"return a JSON array aligned 1:1 to N stories" pattern a local model handles poorly.

**3. Structural segments (intro / outro / section_transition) are music-only placeholders in V1.**
They carry no narration text. This replaces the old prompt's spoken segues ("Turning now to
technology…") with musical stingers — matching the roadmap's own "transitions = stingers" intent.
Their `selected_music` is resolved now via `music.select_music(segment_role=…)`, which finally
exercises Phase 3's role-override path end-to-end (previously unit-tested only, per `ADR-003`).
Consequence: in Phase 4, before mixing exists, these segments produce **no audio** — so the audible
output is the concatenated story narrations. Section transitions become audible only in Phase 5.

**4. Phase 4 records durations but does not mix.** `synthesize_plan` renders each narrated segment,
sets `duration_seconds` on it, and concatenates narration samples into the same single `briefing.mp3`.
`selected_music` rides along on each segment untouched for Phase 5 to consume. No per-segment audio
files are persisted yet — the durationed plan (in the handoff artifact) is the Phase 4 deliverable;
Phase 5 decides how it wants the narration audio (re-render vs. persist).

**5. Section ordering is factored into a shared helper.** `assemble` and the new `tts_prep` must order
sections identically (config order, `Other` last, stories by `source_count` desc) or the audio and the
markdown would disagree. Rather than duplicate the logic, both call a new
`app/pipeline/ordering.order_stories_by_section()`.

## Consequences

### Positive

- Fixes `BUG-005` as a side effect of the restructure, not a separate patch.
- Per-story structure and durations unlock Phase 5 mixing with no further tts_prep changes.
- One LLM call (pronunciation only), robust to failure — no per-segment alignment risk.
- Exercises the intro/outro/transition role-override path end-to-end for the first time.

### Negative

- Drops the old spoken section segues. Between-section flow now depends on Phase 5's musical
  stingers; in the Phase 4 intermediate state there is nothing between sections. Accepted because
  the roadmap always intended transitions to be musical, and the segues were being generated from
  empty markdown anyway (`BUG-005`), so no *working* behavior is lost.
- The narration no longer benefits from an LLM "read-aloud" rewrite pass. Mitigated by draft prose
  already being broadcast-ready; revisit if narration quality regresses in listening.
- `tts_script` is retained (concatenated narration) purely for `qa_gate` and the resume-path guard —
  a transitional redundancy alongside `audio_segments`. Noted for future cleanup.

### Neutral

- Per-segment audio persistence is deferred to Phase 5.

## Alternatives considered

| Option | Why rejected |
|---|---|
| Fix `BUG-005` by moving `tts_prep` after `assemble`, keep the single-blob script | Fixes the bug but not the segmentation; Phase 4 still wouldn't have per-segment durations |
| One LLM call returning a per-story narration array | Local models handle "exactly N aligned array elements" poorly; high misalignment risk for no quality gain over deterministic cleanup of already-clean prose |
| Per-story LLM rewrite (N calls, like frame/draft) | N extra LLM calls per briefing for a rewrite the prose barely needs; disproportionate latency on local Ollama |
| Spoken segues for structural segments | Contradicts the roadmap's "transitions = musical stingers" design and would require generating new content |
