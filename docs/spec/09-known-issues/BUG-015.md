# Bug: BUG-015 Check-then-act race could start two concurrent runs

## Metadata

- Bug ID: `BUG-015`
- Severity: Medium
- Status: fixed
- Found: 2026-07-06 (audit pass, finding R9)
- Fixed: 2026-07-06

## Description

`POST /api/briefings` and `POST /api/briefings/on-demand` each checked for an existing
`status == "running"` Run in one transaction, then created the new Run in a separate transaction —
a check-then-act race window where two near-simultaneous triggers (manual UI, MCP, on-demand)
could both pass the check before either commit. The check also only looked for `"running"`, missing
the window where a just-created Run is still `"pending"` (before the background task flips it).

## Fix

- Broadened both checks to `status.in_(["running", "pending"])`.
- Moved the check into the *same* atomic transaction as the insert (for `start_briefing`, the only
  transaction; for `start_on_demand`, the early check remains as a cheap pre-extraction fast-fail,
  but the check that actually prevents a double-start is re-run inside the same transaction as the
  insert, immediately before it). SQLite's single-writer serialization means a second concurrent
  transaction blocks until the first commits, closing the race.

## Regression tests

`tests/api/test_briefings.py`: `test_post_briefings_returns_409_for_pending_run` (new — covers the
"pending" window gap; the existing `test_post_briefings_concurrent_returns_409` and
`test_on_demand_returns_409_when_run_active` continue to cover the `"running"` case).
