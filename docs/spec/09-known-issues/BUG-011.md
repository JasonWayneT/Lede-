# Bug: BUG-011 Missed-run retry has no user-visible signal

## Metadata

- Bug ID: `BUG-011`
- Severity: High
- Status: fixed
- Found: 2026-07-06 (audit pass, finding R3)
- Fixed: 2026-07-06

## Description

Story 9.3 (`docs/spec/03-feature-specs/9-3-missed-run-detection.md`), AC-1, requires that when a
missed scheduled run is detected, the app shows a banner: "Missed run at 7:00 AM — retrying now."
The retry logic itself (`app/core/scheduler.check_missed_runs`, wired into both `main.py`'s FastAPI
lifespan and `daemon_runner.py`) worked correctly — a missed run is detected and a new Run does
start automatically. But `GET /api/briefings/missed` was a hardcoded stub that always returned
`{"missed_at": None}`, and nothing in the dashboard template rendered a banner for it at all. The
retry fired silently in the background with no way for the user to know it happened or was
happening.

## Impact

- A user could open the app, see a briefing appear (or not) with no explanation of why a run
  started on its own — confusing at best, and masking whether something needed their attention.

## Root cause

The endpoint was left as a placeholder stub after the underlying detection/retry logic (`Story
9.3`) was implemented, and the dashboard was never wired to call it.

## Fix

- `GET /api/briefings/missed` now derives its answer live from `check_missed_runs` (the same
  function used to decide whether to fire a retry at startup) plus a check for any currently
  `running`/`pending` Run, rather than cached process state — this stays correct regardless of
  whether the retry was triggered by the web server's own lifespan startup or by the separate
  daemon subprocess, since both share the same on-disk settings and database.
- The dashboard route (`main.py`) now computes the same `missed_run` context at render time and
  passes a portable, pre-formatted time string to the template (avoiding the non-portable `%-I`
  strftime directive, which is glibc-only and not available on Windows).
- `dashboard.html` now renders a "Missed run at {time} — retrying now" banner (or "— a retry has
  not started yet" if no run is currently active), next to the existing hold-state banner from
  `BUG-006`.

## Regression tests

`tests/api/test_briefings.py`: `test_missed_returns_none_when_no_schedule`,
`test_missed_reports_retrying_when_a_run_is_active`,
`test_missed_reports_not_retrying_when_no_active_run`.

`tests/api/test_dashboard.py`: `test_dashboard_shows_missed_run_banner`,
`test_dashboard_no_missed_run_banner_when_none_missed`,
`test_dashboard_missed_run_banner_shows_retrying_when_run_active`.
