# Known Issue: BUG-002 Settings PUT tests assert JSON-body semantics for endpoints that intentionally moved to Form-encoded bodies

## Metadata

- Bug ID: `BUG-002`
- Status: fixed
- Severity: medium
- Found in: `briefing/tests/api/test_settings.py`
- Fixed in: `CR-002`
- Related requirements: `FR-022`, `FR-026`, `FR-012`
- Related tests: `TEST-012`

## Current behavior

`tests/api/test_settings.py` sends JSON bodies (`json={...}`) to `PUT /api/settings/gmail`,
`PUT /api/settings/schedule`, and `PUT /api/settings/tts`. All three routes were intentionally
switched from a Pydantic JSON body to `Form(...)` parameters in separate commits
(`1fc854c` Gmail, `cfce0a9` TTS, `7281a94` schedule) so the routes match the real
`app/templates/settings.html` UI, which submits plain HTML `<form hx-put="...">` elements
(`application/x-www-form-urlencoded`), not JSON. None of those commits updated the tests.

Because each `Form(...)` parameter has a default value, FastAPI does not error when a JSON body
is posted instead — it silently falls back to the parameter defaults. This produces two classes
of false test failures:

- `test_put_gmail_label` sends `{"label": "My Newsletters"}`; the route never sees it and returns
  the default `"Newsletters"`.
- `test_put_schedule_invalid_cadence`, `test_put_tts_orpheus_no_cuda_returns_400`, and
  `test_put_tts_invalid_engine_returns_400` send invalid values (`"hourly"`, `"orpheus"` w/o CUDA,
  `"coqui"`); the route never sees them either, falls back to valid defaults (`"off"`, `"kokoro"`),
  and returns 200 instead of the expected 400.

A fifth test in the same file, `test_put_tts_kokoro_succeeds`, has the identical defect but
happens to pass, because its JSON payload (`{"engine": "kokoro"}`) matches the Form default the
route falls back to anyway — a false positive that doesn't actually exercise JSON-vs-form
handling.

## Expected behavior

The tests exercise the routes as the real UI calls them: form-encoded (`data=`) requests, so the
values under test actually reach the route and its validation logic.

## Unchanged behavior

- No application code changes — `app/api/settings.py` routes are correct and match the shipped
  HTML-form UI. This is a test-only fix.
- `docs/spec/03-feature-specs/8-4-settings-gmail-configuration.md`, `8-7-settings-schedule-and-daemon.md`
  described a JSON body contract that predates the Form-encoded refactor; corrected as part of this fix.

## Reproduction steps

1. Run `uv run pytest -q tests/api/test_settings.py::test_put_gmail_label`.
2. Observe the response echoes the Form default `"Newsletters"` instead of the posted `"My Newsletters"`.
3. Run `uv run pytest -q tests/api/test_settings.py::test_put_schedule_invalid_cadence` — observe 200 instead of 400.

## Root cause

Test suite was never updated after `app/api/settings.py`'s `gmail`, `schedule`, and `tts` PUT
routes moved from Pydantic JSON bodies to `Form(...)` parameters to match the real htmx-form UI.
