# Bug: BUG-009 Depth and LLM Provider settings forms silently fail to save (BUG-002 recurrence)

## Metadata

- Bug ID: `BUG-009`
- Severity: High
- Status: fixed
- Found: 2026-07-06 (audit pass, finding S2)
- Fixed: 2026-07-06

## Description

`app/templates/settings.html` submits the Depth (`hx-put="/api/settings/depth"`) and AI Provider
(`hx-put="/api/settings/llm"`) forms as ordinary HTML forms — HTMX posts these as
`application/x-www-form-urlencoded`, exactly like the Gmail/Schedule/TTS forms on the same page.
But `update_depth`/`update_llm` in `app/api/settings.py` still declared Pydantic JSON bodies
(`DepthBody`, `LLMBody`). A form submission from the real UI never populates those bodies, so
FastAPI would 422 the request — the same class of defect as `BUG-002`, which fixed this exact
mismatch for the Gmail/Schedule/TTS forms but missed these two.

Note: Settings — Topic Sections (`/api/settings/sections`) was also checked; it has **no
corresponding form in `settings.html` at all** (no UI currently exists for it, consistent with
`CR-007`'s freeform-section interim state), so its JSON body is not mismatched with anything and
was left as-is.

## Impact

- Depth and LLM Provider settings changes made through the actual web UI could never take effect —
  a real, live functional bug affecting two of the more commonly-adjusted settings.

## Root cause

Same as `BUG-002`: the settings routes were originally written with JSON bodies; the UI templates
were switched to plain HTML forms afterward, and only three of the five affected routes were
updated at the time.

## Fix

Converted `update_depth` and `update_llm` in `app/api/settings.py` to `Form(...)` parameters
matching the actual field names in `settings.html` (`briefing_depth`; `provider`, `model_name`,
`api_key`).

## Regression tests

`tests/api/test_settings.py`: `test_put_depth_valid`/`test_put_depth_invalid` and
`test_put_llm_stores_api_key` updated to submit form-encoded data (matching the real UI); added
`test_put_depth_json_body_rejected` and `test_put_llm_invalid_provider_returns_400` as explicit
regression coverage for the form-vs-JSON mismatch class of bug.
