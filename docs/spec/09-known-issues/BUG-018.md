# Bug: BUG-018 Retried runs never recorded processed emails

## Metadata

- Bug ID: `BUG-018`
- Severity: Medium (found while assessing R7 — retry/resume logic duplication)
- Status: fixed
- Found: 2026-07-06 (audit pass, finding R7 follow-up)
- Fixed: 2026-07-06

## Description

While assessing the audit's R7 finding (retry logic duplicated between `orchestrator.run_pipeline`
and `briefings.retry_run`'s nested `_resume` function), a real correctness bug turned up: `_resume`
finalizes a successfully retried Run (`status = "complete"`, `BriefingOutput` written) but never
inserts `ProcessedEmail` rows — unlike `run_pipeline`'s finalize block. A retried run that succeeds
would silently fail to record which emails it processed, so the *next* run would re-fetch and
reprocess the same emails, violating FR-003's no-duplicate-processing guarantee.

## Fix

Added the same `ProcessedEmail` insertion (with the `BUG-012` duplicate-skip guard) to `_resume`'s
finalize block, mirroring `run_pipeline`.

## Regression tests

`tests/api/test_briefings.py`: `test_retry_run_persists_processed_emails`.

## Note on the underlying R7 finding (code duplication)

The duplication itself — `_resume` re-implementing `run_pipeline`'s stage loop, TTS synthesis, and
completion logic rather than sharing it — was **not** refactored in this pass. A shared-helper
refactor is a reasonable follow-up, but touches the orchestrator's core retry/completion path,
which is higher-risk than the other fixes in this pass; it's called out here so future duplication
bugs like this one are easier to anticipate, not silently accepted as invisible.
